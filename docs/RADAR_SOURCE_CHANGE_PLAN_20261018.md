# Radar 來源修改規格（2026-10-18）

## 狀態與目標

使用者已明確授權「開始程式實作」。本文件保留已確認的規格與驗收契約；
RS02～RS06 已完成程式接線、離線驗收並推送；正式來源效果待自然刷新觀察，
測試與發佈狀態以 `docs/HANDOVER.md` 最新紀錄為準。
使用者已另外確認一項產品邊界：AI 應用平台停運納入既有「市佔格局」的
市場退出事件，有資格競爭重點區；不新增第七種事件，不保證自動置頂。

後續澄清：台灣媒體可能僅用「雲端平台、雲端部署」描述 Zeabur 這類服務，
標題與摘要都未寫 AI。因此不能要求 AI 字眼或平台先在小型名單內才收件；
下方已增加繁中服務類型與用途的判斷路徑，已依此完成共用規則與來源接線。

目標是補足 AI 應用／自動化服務的重大營運消息，減少 RuntimeWire 模型目錄
混入新聞，維持現有靜態 Radar、刷新排程與來源治理。日報選題研究另案。

使用者再確認：一般個人相簿與雲端硬碟訂閱不在平台事件範圍；價格與資料
存取權限變更採嚴格認定、避免行銷文；臨時服務中斷須已連續超過 72 小時，
正式永久停運公告可直接收錄，不等待實際停服滿三天。

整體實作範圍已獲授權；上述已確認的內容邊界不需重問。

## 一、INSIDE 入口、層級與健康

- RSS：`https://www.inside.com.tw/feed/rss`。
- 固定身份：`source_id="inside"`、`site_id="tw_media"`、`source="INSIDE"`。
  接受發布者自身 `inside.com.tw` 網域的文章；不從來源內嵌連結新增抓取。
- 使用既有 feed 解析、原發布時間、摘要與引用連結擷取；不讀整頁全文。
- 先過濾、去重，再取最多八則；不得先切 RSS 前八項才篩選，讓非相關文章
  吃掉合格消息。保留 feed 本身的篇數限制，首版不做分頁補抓。
- 先沿用 `tw_media` rank 2、importance 0.56。這是控制首版變數的預設，
  不是完成其新聞正確率評鑑。不得加入整站 AI trusted-source 捷徑。
- 健康沿用 `tw_media.subsources` 的獨立 `inside` 列；有效 feed 無合格文章
  記健康零則，HTML／格式錯誤／缺必要欄位按既有機制記失敗。
- 現有前台對 `tw_media` 原生來源已有媒體分類 fallback；首版可沿用，
  不需要新增導覽、篩選器或版面。

## 二、平台事件如何通過收件與下游 AI 篩選

### 三條收件路徑

1. 原有 AI 新聞：保留現有 AI 標題條件，以及教學／促銷／非 AI 排除規則。
2. 已知平台的重大事件：標題未寫 AI 時，以已確認平台名稱加具體事件判斷。
3. 繁中服務類型的重大事件：即使未知品牌、標題與摘要都沒有 AI，也能依
   雲端部署／應用託管等服務類型、用途及具體事件納入，不必先人工加品牌。

第二路徑首版建議平台名單：Zeabur、OpenCode、n8n、Dify。這四者來自本輪
案例與使用者指定的 INSIDE 背景；名單只是已知服務的辨識捷徑，不是准入白名單。
ASCII 名稱採不分大小寫、明確詞界，不使用文章 URL 中任意子字串代替。

第三路徑專供 INSIDE、iThome、科技新報原生繁中路由，建議使用：

- 較明確的服務類型：「雲端部署」「應用部署」「應用程式託管」「網站託管」
  「PaaS」等；這些類型配上明確營運主體與重大事件即可判斷，無須補 AI 字。
- 較廣的描述：「雲端平台」「雲端服務」「SaaS」「自動化平台」等，搭配
  RSS 標題／摘要描述的應用、網站、程式、資料庫託管或軟體工作流程用途。
  使用者／受影響對象可協助判斷，但不要求文章必須出現台灣、設計師或微型
  創業等特定字樣，也不要求公司在台灣註冊。

例如「雲端部署平台某某宣布年底停止營運」可納入，即使品牌從未登錄、整篇
RSS 材料沒有 AI；「雲端平台某某停止服務，客戶須遷移網站及資料庫」亦可。
僅有雲端股票、機房硬體、天氣用語或籠統 SaaS 趨勢，則不因這些字被放行。
不逐篇搜尋產品背景、不新增 LLM；證據不足時仍可能漏收，但不能將「缺少 AI
或不在品牌名單」本身當作第三路徑的拒收理由。

一般個人相簿、個人雲端硬碟與其訂閱方案明確不在本次平台事件範圍，不能
因使用雲端／訂閱用語、提到已知品牌或附帶 AI 宣傳就走平台事件例外。
本批不另案重寫所有原有 AI 新聞的判斷規則。

重大事件範圍：

- 正式宣布平台永久結束營運、全面停止服務；公告時即可收件。
- 臨時服務中斷已連續超過 72 小時，且符合下述時間證據要求。
- 已發生或已公告的入侵、資料／憑證外洩、要求輪替金鑰等具體資安事件。
- 嚴格符合下述條件的正式價格／方案、付費存取或資料匯出權限重大變更。

### 價格、資料存取權限：嚴格認定

RSS 標題與摘要合看，至少須交代：

1. 具體改了什麼，可辨識原有條件與新條件，例如正式費率調整、取消既有
   基本方案、原可免費匯出的資料改為付費或限制可存取的既有資料。
2. 哪些既有使用者、方案或既有資料受影響；只有新增產品／新客優惠不夠。
3. 已生效，或正式公告的生效安排；預測、建議與未定案說法不算正式變更。

不要求每則都有價格百分比，但不得只有「更划算」「最低幾折」「全面升級」
等形容。以試用、限時折扣、推薦獎勵、新客方案、合作或業配宣傳為主的文章
不走此例外；沒有具體異動證據時直接不納入，不為了判斷而補抓全文或追查
官方方案頁。正式異動不因內文順帶提優惠就必然排除，仍以既有使用者受到
何種具體影響判斷；不得用宣傳詞自行推測變更幅度與重要性。
本次平台價格／權限消息也不能因標題寫 AI 或品牌已在名單中，就繞過嚴格
條件。若同文另有獨立合格的資安等事件，則依該事件證據判斷，不將宣傳內容
冒充正式價格／權限變更。

### 臨時中斷：超過 72 小時才收件

- 以同一次、連續的服務不可用為準，嚴格大於 72 小時；正好 72 小時或
  只有「三天」而無超過證據，不視為已達條件，不能累加多次短暫故障。
- RSS 必須明說已連續超過三天／四天等可確定時長，或提供足夠明確的故障
  起始時間與報導時點／恢復時間。僅寫「近日」「數天」或預估可能停機四天
  不足；期間、時區或是否連續無法確定時不走這條例外。
- 不以抓取時間減文章時間推估停機，不建立自動等滿 72 小時的延後發稿
  任務，不抓狀態頁或建立跨日事件資料庫。現有新聞發布時間／24 小時讀者
  窗口不變；舊報導不會因今天距發表三天就變成新消息。
- 新報導清楚指出中斷已超時，才按其原發布時間進入既有窗口。若報導的是
  超時中斷後恢復，保留已恢復的狀態，不繼續寫成目前停機。
- 臨時中斷本身不標 `market`；有資安等實際證據才附相應既有徽章。
  正式宣布永久停運則按市場退出處理，與這個時間門檻分開。
- 72 小時只限制「單以臨時中斷作為收件理由」；同一事件第一天已有具體
  資安外洩公告時，可依資安條件收件，不必為所有消息一律等三天。

僅有「風險」「更安全」「如何備份」等一般論述，不算已發生事件。平台須為
標題中的事件主體，或在 RSS 摘要同一句明確指認為受影響服務；不能因延伸
閱讀、頁尾品牌名單或背景提及就放行。摘要只作已存 RSS 證據，不新增全文抓取。
對於資料匯出／存取權限的營運消息，可以收進一般列表；沒有對應既有事件
證據時，不強行附加資安、價格或市場徽章。

### 共用規則的最小接線

建議新增一個僅標準函式庫的共用來源範圍模組，例如
`scripts/source_scope.py`，放平台名稱、繁中服務類型／用途、事件與 RuntimeWire URL 判斷。
來源收件和 `scripts/ai_relevance.py` 使用同一份判斷，避免複製兩套字典。

例外僅適用身份與文章網域相符的 INSIDE／iThome／科技新報原生路由，及
RuntimeWire 自有文章。先執行既有教學、危險促銷與排除網域條件，再判斷例外。
不改 OPML／其他來源的規則，不信任任意外部 `accepted=true` 欄位，不需要
新 JSON schema 或持久分類狀態。

符合第二或第三路徑但原 AI 判斷不通過時，以既有 AI 關聯門檻 0.65 納入；理由須
區分已知應用平台事件與繁中雲端部署／託管服務事件。這表示符合 Radar 的
相關範圍，不宣稱服務本身內建 AI，不改寫標題替產品加 AI，也不是「官方公告」。門檻表示可收件，
不是新聞重要性、可靠性或重點保證；若原有 AI 評分較高，不以例外降低。
這個預設會影響 Radar 的 AI 關聯與候選輸出，屬本次已確認的來源範圍修改。

## 三、RuntimeWire 新聞與目錄分流

- 保留同一個 `https://runtimewire.com/rss` 請求、`site_id="runtimewire"`、
  既有 rank 4 與 importance 0.45；顯示名稱由模型媒體改為 AI 媒體。
- 第一關先核對發布者網域及 URL 路徑：只准 `/article/`；`/models/`、
  比較頁及其他路徑不進新聞 archive 的新收件。相同 RSS 不抓第二次。
- 文章沿用現有模型／模型經濟範圍，另准入上述已知平台重大事件；繁中服務
  語彙路徑不自動擴張成 RuntimeWire 全部雲端新聞。以 OR 合併
  規則，避免 OpenCode 消息先被「必須提模型廠商」的舊條件擋掉。
- 合格文章去重後最多十則；目錄、過期與不合格文章不消耗十則額度。
- RuntimeWire 改用既有有效 feed 檢查：feed 正常但全為目錄／過期／不合格
  內容時回傳空列表、健康零則；格式錯誤才失敗。不要順便改 LLM Rumors
  的解析與健康契約。
- 不建立目錄的獨立查漏輸出。LLM Stats、官方來源與現有模型雷達保持原狀。

### 已存目錄資料的過渡

僅停止新收件，仍可能讓最近 24 小時的舊 `/models/` 重新出現。首版必須
共用同一個來源範圍判斷，在組裝兩種讀者列表前排除它們，不能只設
`ai_is_related=false`，因為「全部」模式仍可能顯示。

同時讓既有共享 AI 判斷拒絕 RuntimeWire 非文章路徑，使私人日報從 archive
重建候選時也不再次帶入目錄；不改日報 `daily-news-v2`、優先級、排序或
事件去重規則。這是來源範圍的間接影響，不是日報選題改版。

舊 archive、resolver、翻譯快取照既有保留規則自然退場，不做資料刪除／
遷移，不刷新它們的 last_seen。不得為舊目錄再呼叫翻譯或摘要服務。

## 四、市場退出分類（使用者已確認）

- 不新增事件 code；將完整營運退出納入現有 `market`，讀者仍見市佔格局。
- 要同時有原有 AI 關聯或上述應用部署／託管服務條件、明確營運主體與完整退場動作；使用
  本輪共用來源／平台條件，不單憑「停止」「關閉」「下架」全域匹配。
- 功能移除、模型退役、舊共享叢集停用、區域故障不算平台市場退出。
  公司否認停運的說法也不能當已宣布退出。保留報導的據報／否認等限定語。
- 標題或既有 RSS 摘要有實際入侵證據時，可同時命中 `security`；不能
  因平台停運就推定被駭，或在沒有法律／官方依據時改稱破產。
- 僅給予既有重點候選資格，不保證跨過現有分數／來源門檻，不新增固定
  名次或每期席次。來源仍是媒體，不能因引用官方信件改標官方一手。

## 六、驗收案例與通過條件

以下是驗收契約；實作已用真實 RSS 與合成正反例驗證，具體執行結果與限制
見 `docs/HANDOVER.md`，不以時效不穩的即時網頁當唯一測試資料。

| 案例 | 預期結果 |
| --- | --- |
| INSIDE Zeabur 宣布停止營運，標題沒有 AI | 收進 `tw_media`；共享 AI 判斷可納入，標 `market`；不保證重點名次。 |
| 未登錄品牌的「雲端部署平台某某宣布年底停止營運」，標題與摘要均無 AI | 繁中服務類型加事件成立，收件且標 `market`；不要求補登品牌。 |
| 未登錄品牌的「雲端平台某某停止服務」，摘要說明客戶須遷移網站／資料庫 | 用途與營運主體、事件成立，收件且標 `market`。 |
| 未登錄品牌的應用託管平台遭資料外洩，沒有 AI 字樣 | 類型、主體與具體資安事件成立可收；不因沒有 AI 拒收。 |
| 一般個人相簿、雲端硬碟訂閱漲價或停服 | 不在本次平台事件範圍，不因雲端或訂閱用語放行。 |
| 應用託管平台正式取消既有基本方案，摘要說明受影響用戶與生效安排 | 嚴格價格條件成立可收件；不保證重點席次。 |
| 雲端部署平台新客限時半價、免費試用或「更便宜」宣傳 | 排除價格事件例外；不是既有用戶正式條件變更。 |
| 既有資料匯出改為付費，摘要交代新舊條件、影響方案及生效安排 | 資料權限嚴格條件成立可收；不任意推定資安事件。 |
| 只宣傳新版資料管理更安全／權限更彈性 | 不走權限變更例外。 |
| 部署服務已連續中斷四天，時間證據清楚 | 可收錄臨時中斷；不標成平台退出。 |
| 同一部署服務只中斷兩天、正好 72 小時，或數次短暫故障累計超過三天 | 不走連續超過 72 小時的中斷例外。 |
| 三天前刊出的短暫當機新聞，沒有新的持續中斷證據 | 不因文章變舊而放行，不改發布時間重新入窗。 |
| 預告將維護四天，或只稱中斷數天而無可確認時間 | 不視為已發生超過 72 小時中斷。 |
| OpenCode 要求輪替供應商金鑰的 RuntimeWire `/article/` 新聞 | 收件，媒體身分、rank 4；有入侵／外洩證據才標資安。 |

| 雲端機房硬體消息、籠統 SaaS 趨勢，沒有部署／託管等服務用途或具體重大事件 | 不走平台事件例外。 |

| 取消舊方案與關閉部分舊叢集，平台繼續營運 | 不標市場退出；有其他合格事件則按實際證據處理。 |
| 公司否認關閉平台 | 不標已退出。 |
| RuntimeWire `/models/`，即使標題有 GPT／Qwen／GLM | 不新收件；舊紀錄也不出現在 AI／全部列表、故事與重點輸出。 |
| RuntimeWire 正常模型分析 `/article/` | 保留既有收件能力與層級。 |
| 有效 RSS 全是目錄或無合格新文章 | 健康零則，不增加失敗連續次數。 |
| HTML 假 RSS、壞 XML 或必要欄位全無效 | 明確失敗，不能當健康零則。 |
| 前十項不合格、後面才有合格文章 | 先過濾再限量，合格文章不被提前截掉。 |
| 舊 RuntimeWire 目錄仍在 archive | archive／resolver 不刪，讀者輸出與共享 AI 候選排除；不產生新翻譯。 |
| 已有日報原稿／校稿、選題 policy | 不改寫、不重送；不實作另案選題研究。 |

測試實作只覆蓋上述有意義的跨層行為與相反案例，不為常數增刪寫重複測試。
共用 AI、事件與生成改變後跑完整 Python 測試；來源驗證輸出到 Downloads，
不覆寫 tracked data。使用現成 Node 與 Downloads pytest 暫存目錄；有前端
邏輯變更才需要相應前端驗收，並依既有規則處理資產版本。

## 七、負荷與限制

- 每次實際刷新僅多一個 INSIDE RSS 請求，沿用現有逾時與健康機制；
  RuntimeWire 請求數不增加。實際每日次數依既有排程／心跳執行，不另排程。
- 新增的名稱／服務類型／用途／事件／URL 判斷為本機字串處理，不引入新模型、瀏覽器或 DB。
- 72 小時判斷僅使用既有 RSS 明確時間證據，不增加狀態頁探測、延後工作或
  跨日事件監測。材料不足時不收錄，不以保守性驗證名義增加流程。
- 既有翻譯／摘要的提供者與全域上限不增加；新增候選仍可能改變上限內的
  實際用量，不能宣稱模型成本必定零增加或來源品質因此保證。
- RuntimeWire 停收目錄有望減少候選、翻譯與檔案增長，但 206/242 是既有
  保留資料比例，不是可直接承諾的未來每日降幅。需以實作後真實輸出觀察。
- 單次 feed 成功不證明長期穩定；發布者 feed 深度不足時，首版不靠額外
  分頁、爬文或搜尋補抓。RSS 未提供足夠服務用途／事件證據時仍可能漏收；
  未登錄品牌或未出現 AI 字樣本身，不是繁中服務事件必須漏收的限制。
