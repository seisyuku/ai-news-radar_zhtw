## 1. 目標與既定條件

- 使用者手部受傷，以 iPhone 的 ChatGPT App 語音為優先入口，私人網頁為備案。
- 不要求使用者在 09:00 操作，也不要求 Mac 開機、保持清醒或連網。
- 日報窗口固定為臺北 [前一天 06:00, 當天 06:00)，沒有擴散緩衝。
- 09:00 是系統交付目標；使用者有空時校稿，11:30 是人工發布目標。
- 私人草稿、校稿與原始輸入不提交至公開 repo，不使用公開草稿 artifact。
- 沿用已完成的生成、同 commit 輸入、配對核對與確定性重跑能力。
- 不增加新聞來源、付費抓取、新聞 LLM 摘要或自動發布。
- 閱讀或校稿內容進入 ChatGPT 時，即進入該帳號的對話與資料處理範圍；
  私人雲端儲存不代表內容永遠不離開儲存服務。

## 3. 兩個架構選項

| 項目 | A：外部排程 + GitHub Actions 生成 | B：外部排程 + 獨立雲端 Python 工作 |
| --- | --- | --- |
| 生成程式 | 重用既有 Python 與依賴環境 | 打包既有 Python 程式至獨立服務 |
| 定時來源 | cron-job.org 呼叫 workflow_dispatch | cron-job.org 呼叫私人工作入口 |
| 私人保存 | 生成核對後上傳私人儲存 | 生成核對後上傳同一私人儲存 |
| Mac 依賴 | 無 | 無 |
| 仍有的等待 | GitHub API、runner 與上游快照 | 雲端工作啟動、API 與上游快照 |
| 維護成本 | 較少，沿用現有 CI 與 GitHub | 較多，新增部署與執行環境 |
| 建議 | 第一階段採用 | A 無法通過交付驗收時再評估 |

建議 A。外部觸發繞過 GitHub cron，但不保證 runner 準時；不要以觸發
API 成功代替交付成功。兩方案共享保存與校稿介面，之後改生成環境不必換稿件格式。

## 4. 推薦架構與服務選擇

```text
外部排程 07:15 / 08:15 / 08:45（Asia/Taipei）
      → 日報專用 workflow_dispatch
      → 固定期別及遠端 source commit
      → 下載同 commit 三檔、生成、配對核對、byte-identical 重跑
      → 私人儲存：原稿 / metadata / 校稿 / revision / 交付 manifest
      → 登入後的私人 API
            ├─ ChatGPT 雲端工具入口（先作能力驗證）
            └─ iPhone 私人網頁（同一份稿與版本）
```

平台候選組合為：既有 cron-job.org、GitHub Actions、私人物件儲存，
以及承載私人 API/網頁/MCP 的小型服務。可評估 Cloudflare R2 + Workers，
或使用者已有的同等服務。這是候選選型，離線期間不宣稱現行價格、免費額度、
區域、OAuth 相容性或帳號可用性；復線後先核實再定案。

第一版不購買常駐 VM。Python 在 Actions 執行；前端與 API 不承擔 Python
生成工作。新增日報專用交付 workflow，保留現有公開安全摘要驗證流程。
日報不呼叫新聞刷新；資料太舊時檢查既有更新結果，不強制付費 provider 抓取。

## 5. 觸發、補跑與截止

| 時間 | 建議行為 |
| --- | --- |
| 07:15 | 主要交付。固定觸發時的臺北期別，嘗試生成與保存 |
| 08:15 | 檢查當期有效交付；缺少才補跑，不覆蓋已開始的校稿 |
| 08:45 | 最後一次檢查/補跑；若仍未完成，通知原因與下一步 |
| 09:00 | 系統判定本日準時/未準時，使用者不需操作 |
| 11:30 | 使用者的發布目標，不由本方案自動發布 |

可將三個時段都先交由 Actions 內部 guard 判斷；HTTP 接受只是排程已送達。
外部平台的失敗通知只能證明呼叫層失敗，不能偵測「GitHub 接受但未完成」。
因此交付成功/逾時通知需要另外讀取最終交付狀態，檢查來源也應獨立於 GitHub cron。

日期在 run 建立時固定，不在工作開始或重試時重新推算。若已跨期，標示
missed_issue 並拒絕自動交付；明確指定日期的人工補跑另記。必須記錄
外部送出、run 建立、工作開始、核對及私人保存時間。外部排程若不能提供
日期/請求 ID，需說明這一段的觀測限制，不能冒稱從原定時間端到端固定期別。

第一版每期最多三次定時嘗試；網路/API 有界重試，不啟動無限補跑。
若當期已有 ready 交付，後續只檢查。使用者要求更新快照時建立新版本，
不替換現有校稿。原稿、校稿與「目前選用版本」必須可追溯。

## 6. 私人保存、版本與安全界線

原稿與 metadata 使用既有 input identity 命名，核對後不可變。校稿為獨立
revision，記錄基底原稿 identity、修改時間與修改內容。不同輸入是新原稿版本，
同原稿重跑不再複製校稿。稿件題目使用穩定 ID；顯示第幾則與 ID 分開，
避免重新排序後語音刪錯項目。

上傳原稿和 metadata、讀回核對完成後，最後寫入交付 manifest。
私人服務只顯示具有完整 manifest 的稿；半途上傳不報成功。重跑可恢復，
寫入校稿用 revision 比對，拒絕手機網頁與 ChatGPT 同時修改造成的靜默覆蓋。

私人儲存禁止匿名讀取；使用 HTTPS；登入只允許維護者。網址不可代替登入。
前端/手機不持有儲存管理權限或 GitHub PAT。外部觸發憑證、原稿上傳、
校稿修改與讀取權限分開；PAT 限既定 repo 的 Actions 寫入，存外部服務設定。
GitHub 日報交付 workflow 不攜帶新聞 provider/LLM 憑證。

公開 logs/Step Summary 只留固定狀態、期別、commit、as-of、題數與核對結果，
不留草稿、原始輸入、任意 exception、登入 token 或私人完整網址。
既有公開網站、資料與新聞刷新 workflow 維持原功能。

新雲端保存期提議：原稿/校稿/版本 90 天、診斷及輸入 7 天；這是待裁決的
保存政策，不授權自動刪除。先提供匯出，再另行啟用清理。既有本機私人稿
不搬移、不刪除、不自動上傳。雲端上傳內容僅為本方案新生成的私人產物。

## 7. 手機與語音操作

### ChatGPT 優先路線

驗證雲端工具的登入與可用性後，提供小範圍工具：讀取日報狀態、讀取指定稿、
按穩定題目 ID 套用編輯、讀回目前 revision、請求當期有界重試。
第一版不提供發布、任意 shell、repo 寫入或付費新聞刷新工具。

口述例子：

- 「讀出今天的新聞標題。」
- 「只保留第一、第二、第十一、第十五、第十六則。」
- 「校稿第一和第十六則。」
- 「讀出修改後版本。」
- 「重試今天日報。」

寫入成功必須有後端回應與讀回確認；不能把 ChatGPT 說「已修改」視為保存
證據。編輯回應帶期別/revision與變更摘要。刪除為校稿排除，可復原。
口述遇到不明確題號、不同日期或版本不一致時，不猜測批次修改。

ChatGPT 的工具處理、編輯或來源核對會使用帳號額度；純生成沿用原程式，
不另外呼叫 LLM API。持續語音可用性、通知與工具授權畫面需實機測試，
「語音輸入能送出文字」不等於「持續語音能完成所有雲端工具操作」。

### 私人網頁備案

登入後直接呈現：今天狀態、稿件日期、資料時間、題數、全文、來源、
保留/排除、標題/摘要修改、保存、還原、版本與匯出。每則獨立欄位，
大按鈕、明確可存取標籤，支援 iPhone 語音控制與聽寫。
不得依賴只在特定瀏覽器可用的 Web Speech API；第一版使用系統聽寫。
朗讀先驗證 iOS 系統/ChatGPT 支援，不預設新增付費 TTS。

ChatGPT 接入失敗時，私人網頁可先交付；不得宣稱已滿足首選 App 操作。
若無法做到手部零操作，要明確記錄登入/授權/導航仍需協助的步驟。

## 8. 狀態、異常與通知

| 狀態 | 意義與處理 |
| --- | --- |
| pending/running | 已請求或執行中，沒有正常交付 |
| ready-for-review | 時效/配對/重跑/私人保存核對完成；不代表新聞已查證 |
| review-only | 過舊、未達截止、未知或未來快照，不作正常當期稿 |
| failed | 必要輸入、生成、核對、上傳或寫入失敗，保留舊成功版本 |
| missed_issue/late | 固定期別已跨日或晚於交付期限，不能改期掩蓋 |

通知只含期別、狀態與受保護入口，不含新聞全文。首次成功通知一次；補跑
成功更新狀態；失敗達最後時段再通知，避免每次輕微重試都打擾。
通知渠道在 C00 選定；若採 email、訊息服務或手機推播，其傳送及帳號連接
需納入核准範圍。不能假設 cron-job.org 自己的 HTTP 通知能涵蓋交付故障。

Mac 關機不影響雲端；手機離線不影響生成，但閱讀/保存需要網路。
真正離線口述不保證能連雲端；可先記錄修改，復線後比對 revision 再同步。
零題的新鮮合法日報可 ready，但顯示零題及 coverage 限制；過舊零題不能宣稱
當天沒有新聞。任何新聞網頁內容都只當資料，不當工具指令或發布授權。

## 11. 最終驗收

- Mac 關機時雲端仍成功產稿；使用者不用在 09:00 操作。
- 新流程連續三個完整臺北日，每日都有外部觸發證據及 09:00 前完整私人交付。
- 檢查外部請求/排隊/生成/保存完整時間，不將 HTTP 2xx 或 Actions 綠燈當交付證據。
- Mac 外的 iPhone 可以登入，閱讀今日稿並用語音完成一次選題、修改、讀回。
- 網頁與 ChatGPT 共用同一 revision，衝突被拒絕，重跑不覆蓋校稿。
- 模擬/實測下載失敗、資料太舊、上傳中斷、憑證失效與重複觸發；舊成功稿保留。
- 原稿/metadata 核對、相同 bytes 重跑與來源 commit 可追溯。
- 匿名訪問被拒；公開 repo/artifact/log 不含私人稿、輸入與憑證。
- 失敗通知與補跑可用；真空日與資料不足清楚區分。
- 發布工具未啟用；使用者確認後手動發布的流程另記，不能把交付算成已發布。

舊 O01 的「兩種 event=schedule 都出現」是舊 cron 方案條件，不能用外部
workflow_dispatch 假裝達標。核准新架構後明確改版驗收條件，保留舊方案
未通過紀錄，再累積新方案的三日證據；不能事後重定義舊 run 成功。
