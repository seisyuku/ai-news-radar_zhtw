A More Predictable Release Cycle for MCP

來源摘要（原文）
We’ve spent a lot of time over the past two years talking about ways to improve MCP, add new features and capabilities, and get on a more predictable release cadence. Clearly, there has been no shortage of ideas both from the maintainer and broader developer community. Getting those ideas reviewed, implemented, tested, and into a release is a whole other part of the job, and we want to make that specific part easier to follow for our community. For folks working on proposals, that means knowing when reviews will happen and how much time there is to make adjustments. SDK maintainers also need to know when the spec will stop changing - both client and server developers use our developer toolchain as a starting point to try new MCP capabilities out and share feedback. To make this process easier, we’re setting up a more consistent timeline for upcoming spec changes so that you don’t have to piece a schedule together from meeting notes and GitHub threads. The Core Maintainers worked through these questions together at MCPCon Europe, and Kurtis Van Gent recently wrote up the process in SEP-3398: Release Cycle Updates - this is our de facto release guidance moving forward. As a result of this work, we’re moving MCP specification releases to a regular six-month schedule. Two releases a year # We’ll generally publish specification releases on the last Tuesday of March and September . Alongside each release date, we’ll share the proposal deadlines and SDK beta dates, so you can work backward from them when planning your own implementation and testing.
